It illustrates the main functionalities offered by the system by showing the key interactions between external actors and the system. The use case diagram is used to identify who the actors are and what services (use cases) each actor can access while interacting with the system. It helps in understanding the functional behavior of the system from the user’s perspective. In addition, the diagram defines the relationships between different use cases through the use of include and extend notations, which represent mandatory and optional interactions between system services. Overall, the use case diagram defines the system boundaries and clarifies the roles and responsibilities of all actors involved in the system./Figure 1: ZAD Use Case Diagrams3.3 System ModelsThe models utilizing UML diagrams for demonstrating the operation of a proposed system include schematic diagrams, workflow diagrams, and structural diagrams. The system follows a distributed client–server architecture, where mobile and web interfaces communicate with backend services through secure APIs. This architectural design ensures scalability, maintainability, and reliable data management, while supporting multiple actors, including individuals, restaurants, charitable organizations, and administrators.In addition, the architecture supports key system features such as donation management, surplus redistribution, integrated payment services (both online and cash), and QR-based pickup confirmation. These components work together to ensure efficient coordination between users and service providers within the platform.3.4.1 Sub-System (descriptions of the sub-systems and their services)Each sub-system of the ZAD system provides a specific set of services as follows:User Mobile Application (Client Sub-System)This sub-system focuses on user interaction and allows individuals to register and log in, browse and search food offers, view offer details, reserve or cancel food packages, track order status, select payment methods (online or cash), navigate to pick-up locations, and submit complaints or feedback. Users can also submit food donations to charitable organizations through the application.Restaurant Interface (Client Sub-System – Mobile / Tablet / Web)This sub-system enables restaurants to manage their activities on the platform, including viewing reservations, creating and managing surplus food packages, editing or closing listings, managing Account information, confirming pickups by scanning QR codes, and donating surplus food to charitable organizations. Restaurants can also view payment statuses related to their reservations.Charitable Organization Interface (Client Sub-System – Web)This sub-system allows charitable organizations to manage donation activities by reviewing submitted donations, accepting or rejecting donations, scheduling pickups, confirming donation receipt, viewing donation history, generating donation reports, and publishing remaining surplus food for redistribution when available.Administration and Control Sub-System (Admin Web Dashboard)This sub-system is used by administrators to monitor platform activities, manage user, restaurant, and charitable organization accounts, validate registrations, handle complaints and reports, resolve conflicts, moderate food offers, and enforce system policies and regulations.Support Services Layer (API / Server Sub-System)This is the core backend sub-system responsible for coordinating communication between client interfaces and managing business logic. It handles operations such as managing food offers, maintaining reservation records, generating QR codes, updating order statuses, processing donation workflows, and triggering notifications based on system events. This layer also integrates with external services such as payment gateways and location-based services.Data Management and DatabasesThis sub-system is responsible for storing and managing all system data, including user accounts, restaurants, charitable organizations, food offers, reservations, donations, payment transactions, QR code data, complaints, and reports. It ensures data consistency, integrity, and availability across the entire system.Notification ServiceThe notification service is responsible for sending real-time notifications to users, restaurants, and charitable organizations based on system events, such as reservation confirmations, pickup reminders, donation updates, payment confirmations, and administrative actions.	3.4.2 Software ArchitectureThe ZAD system follows a layered software architecture that separates the system into three main layers: the UI Layer, Business Logic Layer, and Infrastructure Layer. Each layer has a specific responsibility and communicates with the adjacent layers through well-defined interfaces. This design improves modularity, scalability, maintainability, and system clarity.UI Layer (Presentation Layer)The UI Layer is responsible for all user interactions with the system. It provides mobile and web-based interfaces for individuals, restaurants, charitable organizations, and administrators. This layer allows users to perform actions such as authentication, browsing and searching food offers, viewing offer details, making reservations, selecting payment methods, tracking reservation status, confirming pickup using QR codes, submitting donations, and providing ratings or complaints.The main UI components include:Authentication InterfaceOffer Browsing & Offer Details InterfacesReservation & Reservation Status InterfacesQR InterfaceMap & Navigation InterfaceRating & Feedback InterfaceReport / Complaint InterfaceProvider Portal Interface (for restaurants and charities)Admin Dashboard InterfacePayment Method, Checkout, and Payment Status InterfacesThe UI layer does not contain business logic; it only collects input from users and displays System responses.Business Logic Layer (Application Layer)The Business Logic Layer contains the core processing logic of the system and enforces all business rules. It handles the coordination between different actors and manages system workflows.The main components of this layer include:Auth & RBAC Component: manages authentication and role-based access control.Provider & User Management Component: manages users, restaurants, and charitable organizations.Offer Management Component: manages food offers and surplus packages.Reservation Management Component: handles reservations and conflict prevention.QR Management Component: generates and validates QR codes for pickup confirmation.Pricing Rules Component: enforces low-price and free-offer policies.Payment Management Component: handles online and cash payments.Notification Component: sends system notifications.Map/Location Integration Component: integrates location-based services.Trust & Support Component: manages ratings, complaints, and reports.Admin Services Component: provides administrative control and monitoring features.This layer is the brain of the system and ensures correct execution of all system processes.Infrastructure Layer (Data & External Services Layer)The Infrastructure Layer is responsible for data storage and integration with external systems. It does not contain business logic and has no direct user interface.This layer includes:MySQL Database: stores all system data such as users, restaurants, charities, offers, reservations, payments, donations, ratings, and complaints.Firebase Services: provides authentication support and real-time notifications.Maps / Location API: provides geolocation and navigation services.External Payment Gateway: processes online payments and returns transaction status.This layer ensures data consistency, reliability, and secure integration with external services.Benefits of the Layered ArchitectureThe layered architecture provides several key benefits:Modularity: Each layer can be modified independently with minimal impact on other layers.Scalability: Layers can be scaled separately based on system load.Maintainability: Clear separation of concerns simplifies debugging and future updates.Flexibility: Infrastructure technologies (e.g., databases or APIs) can be replaced without affecting application logic.Reusability: Components can be reused and extended in future system enhancements./Figure 12: ZAD Architecture Diagram3.4.3 Deployment diagramThe deployment diagram shows how the ZAD system is physically deployed in a distributed client–server environment. ZAD connects restaurants, charitable organizations, and individuals through one integrated platform, allowing providers to publish surplus food offers while enabling users to reserve and collect them within defined pickup time windows. ZAD supports two distribution modes: Free donations, mainly for charitable organizations and also available for individuals and Low-price offers, which can be used by restaurants (surplus packages) and individuals (symbolic-price offers) to support access to food while maintaining dignity for those in need.The system is built using a client–server architecture, where a mobile application is used by individuals and charities, and web-based dashboards are used by restaurants and administrators. Location-based services are integrated to help users discover nearby offers, while a structured reservation workflow with QR-code confirmation ensures accurate pickup and prevents conflicts such as double reservations.This report defines the system’s functional and non-functional requirements and includes UML diagrams that describe the system behavior and structure, such as use case diagrams, activity/state diagrams, class diagrams, component/architecture diagrams, and a deployment diagram. Overall, ZAD provides a practical and efficient solution for managing surplus food offers and reservations in an organized and secure manner.4.2 Next Semester PlanWeek 1–2: Setup &
